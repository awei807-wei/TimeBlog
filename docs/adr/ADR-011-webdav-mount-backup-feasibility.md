# ADR-011 草案：WebDAV 本地挂载作为备份目标的可行性评估报告

> 状态：**评估报告（建议稿）** — 只读分析，未对代码/部署做任何改动。
> 范围：评估"把备份数据放到 VPS 本地挂载的 WebDAV 目录里"这一方案的可行性与风险。
> 关联：ADR-010（拉取式备份）、deploy/backup.sh、deploy/nas-pull-backup.sh、deploy/restore.sh。

---

## 0. 结论摘要（TL;DR）

**用户的"把备份放到 VPS 本地 WebDAV 挂载"想法，作为"主备份目标"是不可行/不推荐的**，核心原因是它与 ADR-010 的安全目标**直接冲突**：一旦 WebDAV 挂载在 VPS 本地，VPS 进程就持有对备份目标的**写/删权限**，等于把"NAS 历史快照防篡改"的信任边界从 NAS 搬回到了 VPS 上——这正是 ADR-010 明确要避免的。

**推荐方案：方向一（保留拉取模型）**，即 WebDAV 只作为 **NAS 侧**的传输/落盘目标：NAS 从 VPS 以只读 rsync/SSH 拉取、校验后，再把快照写入 NAS 本地的 WebDAV 挂载。这样既保留了"VPS 无写权限"的安全边界，又满足了"备份落到 WebDAV/NAS"的需求。

**方向二（VPS 主动推送到本地 WebDAV 挂载）会破坏安全模型**，除非把 WebDAV 目标设计成"VPS 只读、NAS 负责写"——但那就不再是"VPS 本地挂载"了，而等价于方向一。

WebDAV 本身**不适合作为需要原子快照 + SHA-256 校验的备份主存储**（尤其 davfs2/fuse 挂载），更适合作为**二次/异地副本**。详见下文。

## 1. WebDAV 挂载的技术特性与风险（davfs2/fuse）

### 1.1 本质：WebDAV 不是 POSIX 文件系统
davfs2/fuse 把 HTTP 上的 WebDAV 资源"伪装"成本地 POSIX 目录，但这层伪装有大量语义缺口：

| 能力 | davfs2/fuse 表现 | 对备份的影响 |
|------|------------------|--------------|
| **缓存** | 默认启用内核页缓存 + davfs2 用户态缓冲；写路径先落到本地缓存，**异步/延迟刷写**到远端 | **崩溃/断连时缓存数据可能未落盘**，出现"本地看着写了、远端没有"或半写状态 |
| **原子性** | 不提供跨文件原子语义；单文件 PUT 也不是原子的（WebDAV 无事务） | 无法保证"一个快照要么完整出现、要么不出现" |
| **rename 语义** | davfs2 对 rename 通常拆成 COPY+DELETE，非原子；且可能因服务器不支持 `MOVE` 而退化为复制 | **mv 快照目录不原子**，与 nas-pull-backup.sh 的 `mv -- "$TMP_DIR" "$DEST"` 原子落盘假设冲突 |
| **文件锁** | WebDAV 锁（LOCK/UNLOCK）在 davfs2 中支持有限、davfs2 默认不强制锁；不同客户端锁语义不一致 | 并发写/并发挂载无可靠互斥 |
| **大文件** | 超过服务器/代理限制（如 nginx `client_max_body_size`）的 PUT 会失败；断点续传依赖 davfs2 配置 | media.tar.gz 可能很大，需确认服务器限制 |
| **并发写** | 多挂载点/多客户端同时写同一文件无合并，后写覆盖 | 与 NAS 保留策略并发删除冲突风险 |
| **权限 0600** | WebDAV 服务器通常**不保留** POSIX 权限位；davfs2 本地看到的 0600 只是本地 umask 的"视图"，远端并不强制 | **0600 只是假象**，远端任何有 WebDAV 权限的账号都能读 |
| **校验和/哈希** | WebDAV 传输层（HTTP/1.1）**不内建端到端校验**；davfs2 不维护 SHA-256；数据完整性只能靠应用层 `sha256sum` | 传输中损坏无法自动发现，**必须依赖应用层 SHA-256 校验**（本项目已有，见 backup.sh/nas-pull-backup.sh） |
| **断线重连** | davfs2 有 `delay_upload`/自动重连，但**不是强一致**；断连时写可能排队或静默失败 | 备份可靠性依赖挂载稳定性 |

### 1.2 结论：WebDAV 不适合作为"原子快照 + SHA-256 校验和"的备份主存储
- **原子快照**：davfs2 不提供原子 rename/目录级事务，快照"要么完整要么没有"无法保证。
- **SHA-256 校验**：本项目**已经**在应用层做 `sha256sum`（backup.sh 生成、nas-pull-backup.sh 校验），所以校验和本身可保留；但 WebDAV 传输层不保证完整性，校验必须在**写入后、且从远端重读**时再做才有意义——而 davfs2 缓存可能让"重读"读到的是本地缓存，掩盖真实损坏。
- **保留策略**：`rm -rf` 删除在 davfs 上可行但非原子、无回收站语义，误删/半删风险高。

**WebDAV 更合适定位**：作为**归档/异地副本**（只写一次、很少删、可容忍最终一致），而非需要强一致、原子、可校验的**主备份**。

## 2. 与拉取模型的安全权衡（关键）

### 2.1 现有安全模型（ADR-010）
- VPS 只生成**带 SHA-256/manifest 的暂存备份**（backup.sh 产物）。
- **NAS 主动**以只读 SSH/rsync 拉取，校验后**在 NAS 本地**原子创建时间戳快照并执行保留策略。
- 设计目标：**VPS 被入侵时不应持有删除 NAS 历史快照的权限**；**NAS 停机不影响生产**。

### 2.2 冲突分析：把 WebDAV 挂载在 VPS 本地 = 破坏信任边界
如果 WebDAV 挂载在 VPS 本地（`/mnt/webdav`），那么：
- VPS 上的**任意进程（含被入侵后提权的攻击者）** 对 `/mnt/webdav` 拥有与挂载权限一致的**读/写/删**能力。
- 攻击者可直接 `rm -rf /mnt/webdav/<历史快照>` 或篡改快照内容 / SHA256SUMS，**删除或伪造 NAS 历史备份**。
- 这与 ADR-010"VPS 不应持有删除 NAS 历史快照权限"**直接冲突**。

**关键区分**：
- **WebDAV 挂载在 NAS 侧**（NAS 主动拉取后写入 WebDAV）→ VPS 对 WebDAV **无直接写权限**，安全边界保留。✅
- **WebDAV 挂载在 VPS 本地**（无论方向一/二，只要 VPS 进程能写）→ VPS 持有对备份目标的写/删权限，**信任边界被打破**。❌

> 补充：即便技术上把 VPS 侧挂载做成"只读"，攻击者仍可能通过 VPS 上已持有的凭据/进程**操纵挂载**或**删除本地挂载点内容**；"只读挂载"也难以阻止攻击者利用 VPS 上的备份工具链（backup.sh 等）向 WebDAV 写入恶意内容。因此**安全上不应依赖"VPS 本地挂载 + 只读"来保护备份**。

### 2.3 威胁模型小结
| 场景 | VPS 被入侵 → 攻击者能否删/改 WebDAV 历史备份？ |
|------|-----------------------------------------------|
| WebDAV 挂载在 **VPS 本地**（可写） | **能**（直接 `rm`/改写）——破坏 ADR-010 |
| WebDAV 挂载在 **NAS 侧**，NAS 拉取后写入 | 不能（VPS 无写路径）→ 保持 ADR-010 |
| WebDAV 挂载在 VPS 本地但**只读** | 部分缓解，但不可依赖；且需额外读写分离机制，复杂度高 |

## 3. 两种可行方向

### 方向 a：保留"拉取"模型，WebDAV 作为 NAS 侧传输/落盘目标（✅ 推荐）
- **架构**：NAS 用**现有 nas-pull-backup.sh** 从 VPS 只读拉取 → 校验 → 在 NAS 本地原子创建快照 → **再**把快照同步/复制到 NAS 本地的 WebDAV 挂载（如 `/mnt/webdav/<stamp>/`）。
- **对现有代码的影响**：**几乎为零**。nas-pull-backup.sh 的 `DEST_PATH` 指向 NAS 本地目录即可；WebDAV 只是 NAS 上的一个"落盘目标"，可在脚本末尾追加一步 `rsync -a "$DEST" /mnt/webdav/`（NAS 侧执行）。
- **安全**：VPS 对 WebDAV 无写权限，ADR-010 边界保持。
- **注意**：NAS→WebDAV 的这一步是**推送到远程 WebDAV**，仍受 WebDAV 原子性/完整性限制；建议**在 WebDAV 落地后再次 `sha256sum -c`**，且 WebDAV 只作为**二次副本**，NAS 本地仍保留主快照。

### 方向 b：改为"VPS 主动推送"到本地 WebDAV 挂载（❌ 破坏安全模型）
- **架构**：VPS 上 backup.sh 产物直接写进 `/mnt/webdav`（VPS 本地挂载）。
- **安全**：**破坏 ADR-010**。VPS 进程持有对备份目标的写/删权限，攻击者可删/改历史快照。除非把 WebDAV 挂载点对 VPS 设为只读且由 NAS 侧写——那已不属于"VPS 主动推送"，等价于方向 a。
- **代码改动**：需改 backup.sh（BACKUP_DIR 指向 WebDAV）或新增"推送"脚本；同时放弃现有的 NAS 拉取/校验/保留逻辑，或保留后造成双写。
- **结论**：**不推荐**，除非明确接受"VPS 被入侵可删备份"的降级。

## 4. WebDAV vs rsync/SSH 拉取能力对比

| 能力 | rsync/SSH 拉取（现状） | WebDAV |
|------|------------------------|--------|
| **校验和** | rsync 增量校验 + `sha256sum` 应用层 | 无内建端到端校验；需应用层 `sha256sum`，且受缓存影响 |
| **原子快照** | NAS 本地 `mv` 原子落盘 | 不原子（rename 拆 MOVE/COPY+DELETE） |
| **保留策略** | NAS 本地 `rm -rf` + 严格时间戳校验 | 远端 `rm` 可行但非原子、无事务 |
| **断点续传** | rsync `--partial` 原生支持 | davfs 依赖 `--partial` 类配置，稳定性弱 |
| **增量** | rsync 增量传输省带宽 | WebDAV 基本全量 PUT，无增量 |
| **权限保留** | rsync `-aH` 保留 | WebDAV 不保留 POSIX 权限 |
| **断连语义** | rsync 失败可安全重试 | davfs 缓存延迟写，断连可能丢/半写 |
| **传输开销** | 高效（增量） | 高（全量、HTTP 头开销） |

**结论**：WebDAV 在"校验和、原子快照、保留策略、断点续传"上**全面弱于** rsync/SSH。它**不能**承载现有备份的核心正确性需求，只能作为低成本**副本/归档**。

## 5. 网络 / 性能 / 可靠性

- **延迟**：远程 WebDAV 每次操作都走 HTTP 往返（list/stat/put/delete 各自一次），高延迟下快照创建/保留策略的目录遍历会显著变慢。
- **带宽**：WebDAV 全量 PUT，无增量；大文件（media.tar.gz）在带宽受限时耗时且易超时。
- **断连**：davfs 缓存延迟写，断连时可能**静默丢数据**或产生半写文件；对"备份必须完整"的要求是硬伤。
- **建议**：**WebDAV 只作为二次/异地副本**。主备份仍走现有 NAS pull（rsync/SSH），保证本地原子快照 + 校验；WebDAV 副本用于异地容灾，可容忍其非原子、非强一致特性，并在写入后做一次 `sha256sum` 复核。

## 6. 明确结论与注意事项

### 结论
1. **"把备份放到 VPS 本地挂载的 WebDAV"不可行（作为主备份）**，且与 ADR-010 冲突。
2. **推荐方向 a**：保留拉取模型，WebDAV 作为 **NAS 侧落盘/二次副本**；对现有代码改动最小（NAS 侧追加 rsync 到 WebDAV），安全边界保持。
3. **方向 b（VPS 主动推送到本地 WebDAV）不推荐**，除非接受安全降级。

### 需要注意的坑
- **权限 0600 不保留**：WebDAV 远端不强制 POSIX 权限，备份文件在 NAS/WebDAV 侧可能被其他账号读取；需用 WebDAV 侧 ACL/目录权限 + NAS 侧 0600 环境文件（root-owned）双保险。
- **原子性缺失**：快照落盘必须用"临时目录 + 最后 rename"，且 rename 在 davfs 上不原子，需在 NAS 本地先落盘再同步到 WebDAV。
- **SHA-256 校验**：必须在写入后从**远端**重读校验，避免读到 davfs 本地缓存；对 WebDAV 副本，建议 NAS 落盘后再对 WebDAV 侧文件 `sha256sum -c`。
- **大文件**：确认 WebDAV 服务器/反向代理的 `client_max_body_size` 高于最大备份文件。
- **断连/静默失败**：WebDAV 副本写入后必须显式校验，且设置合理超时/重试；不要把 WebDAV 当唯一备份。
- **保留策略**：远端 `rm` 非原子，建议保留策略只在 NAS 本地执行，WebDAV 副本用"只增不删"或独立 TTL。

## 7. 附：对现有脚本的影响（只读评估，未改动）

- **backup.sh**：无需改动（方向一）。若走方向二才需改 BACKUP_DIR。
- **nas-pull-backup.sh**：无需改动（DEST_PATH 指向 NAS 本地）；新增 NAS→WebDAV 的同步步骤为可选扩展。
- **restore.sh**：恢复仍应从 NAS 本地主快照进行；WebDAV 仅作异地恢复源时需先 `rsync` 回 NAS 本地再恢复。
- **ADR-010**：方向一不违反；方向二违反，需新 ADR 明示安全降级。
