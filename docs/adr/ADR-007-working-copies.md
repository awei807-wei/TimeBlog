# ADR-007：工作副本与正式内容分离

- 状态：已接受
- 决策：自动保存只更新 `entry_working_copies`；正式保存才更新 `entries`、关系、媒体引用和版本快照。
- 原因：作者编辑公开文章时，匿名访客继续看到上一次正式版本；同时支持多份未命名草稿。
- 后果：同步接口必须带 client draft ID、revision 和幂等语义；恢复工作副本不覆盖正式历史。
- 分类和标签字段保留“未提供”和“显式空数组”的区别：未提供时继承工作副本，传 `[]` 时清空已有关系。标签字段省略时继续按既有规则合并正文 hashtag；一旦显式提供数组，数组内容是权威值，不再从 Markdown 补回 hashtag。
- 持久化撤销接口与内存实现均返回 `entry`，其中包含撤销前工作副本的编辑字段，供编辑器回填。

## 文章编辑的一致性约束

- `entries` 是当前正式内容，`entry_versions` 是提交时写入的不可变版本快照（文章最多保留最近 20 个快照），`entry_working_copies` 是自动保存的未提交工作副本。三者不是 A/B 发布版本；因此编辑器看到的工作副本内容可能与公开页的正式内容不同，直到用户明确提交保存。
- 已有文章的编辑草稿使用 `edit-<entryUUID>-<generation>` 作为客户端草稿 ID。该类草稿只允许更新已存在的 generation；提交或恢复公开版本后，旧 generation 的迟到自动保存必须返回 `409`，不得重新创建孤儿草稿或覆盖刚重建的 generation。
- 持久化的打开编辑、提交和恢复公开版本操作统一按“工作副本行 → 正式 entry 行”的顺序加锁；提交会在事务内重新加载并锁定工作副本，恢复操作会锁定并清理旧 generation 后重建新工作副本，避免并发请求互相覆盖或死锁。
- `journalTime` 遵循三态语义：请求缺少该字段时继承工作副本值，历史工作副本缺少该字段时继承正式 entry 的值；显式传 `null` 清空时间；传具体值则写入该值。不能把“缺少”和“显式清空”混为一谈。

## 管理端可见性

编辑已有公开文章时，管理端显示正式版本的 revision、更新时间和 canonical slug，并明确提示“自动保存的是未发布草稿，公开页仍显示上次保存版本”。存在未提交修改时提供查看公开版本和显式放弃修改并恢复公开版本的操作；不会把未提交工作副本误标为公开版本。
